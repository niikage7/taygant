# Запрос к бэкенду: механизм контрольных точек

Составлено фронтендом по итогам работы с `internal/service/milestones.go`,
`internal/models/milestone.go` и `internal/models/task.go`.
Два независимых пункта — второй можно делать без первого.

---

## 1. Веху невозможно отметить достигнутой (баг)

**Что видит пользователь.** В обзоре «закрыто вех» всегда 0, даже если веха
фактически пройдена.

**Причина.** Статус выводится из `ActualDate`:

```go
// internal/service/milestones.go, deriveMilestoneStatuses
if milestones[i].ActualDate != nil {
    milestones[i].Status = models.MilestoneStatusDone
    continue
}
```

При этом `MilestoneInput` принимает только `Code`, `Name`, `PlannedDate`.
Ни `Create`, ни `Update` не трогают `ActualDate`. Поиск по коду показывает
единственное место, где поле заполняется, — `database/seed.go`.

Итог: у вехи, созданной через API, `ActualDate` навсегда `nil`, статус `done`
недостижим, `MilestonesClosed` в дашборде всегда считает только засеянные вехи.

**Что просим.** Принимать фактическую дату в `PATCH /milestones/{id}`:

```go
type milestoneRequest struct {
    Code        string       `json:"code"`
    Name        string       `json:"name"`
    PlannedDate models.Date  `json:"plannedDate"`
    ActualDate  *models.Date `json:"actualDate"` // новое
}
```

Важно: именно указатель с различением «поле не передано» и `null`. Первое —
не менять, второе — снять отметку о достижении (веху закрыли по ошибке).
Сейчас `Update` перетирает все поля из тела, поэтому фронт при переименовании
вехи не должен случайно сбрасывать её фактическую дату.

Фронт готов: как только поле появится, добавляем кнопку «Отметить достигнутой»,
менять на нашей стороне больше нечего.

## 2. Задачи не привязываются к вехе (доработка модели)

**Чего не хватает.** В `models.Task` нет ссылки на веху — только `SprintID`,
`ParentTaskID` и флаг `IsMilestone`. Поиск `MilestoneID` по бэкенду не находит
ничего, кроме параметров пути в роутере.

Из-за этого нельзя ни показать «какие задачи ведут к вехе», ни посчитать по ней
прогресс. Пользователи этого ждут: в трекерах веха обычно агрегирует работы.

**Что просим.**

1. Поле в модели:

```go
// models.Task
MilestoneID *uuid.UUID `gorm:"type:uuid;index"`
Milestone   *Milestone `gorm:"foreignKey:MilestoneID;constraint:OnDelete:SET NULL"`
```

`SET NULL`, а не `CASCADE`: удаление вехи не должно уносить с собой задачи.

2. Приём `milestoneId` в `taskCreateRequest` и `taskUpdateRequest`
   (указателем, семантика как в п.1: не передано — не менять, `null` — отвязать)
   и отдача в `taskDTO`.

3. Валидация: веха должна принадлежать тому же проекту, что и задача, иначе
   409/400.

**Желательно, но не обязательно:**

- фильтр `GET /projects/{id}/tasks?milestoneId=...` — чтобы не тянуть все задачи
  и не фильтровать на клиенте;
- в `milestoneDTO` счётчики `tasksTotal` и `tasksDone` — иначе для прогресса
  каждой вехи фронт делает отдельный запрос за задачами.

**Что сделает фронт после этого:** выбор вехи в форме задачи, группировка
реестра по вехам, прогресс и список работ в карточке вехи.

---

## Что уже сделано на фронте без изменений бэкенда

- Контрольные точки проекта выводятся на таймлайне Ганта пунктирными отметками
  (данные приходили в ответе `/gantt`, но не использовались).
- В легенде разведены «задача-веха» (`Task.isMilestone`) и «контрольная точка
  проекта» (`Milestone`) — это разные сущности, и их путали.
- В диалоге вех написано, что отметить веху достигнутой пока нельзя, со
  ссылкой на причину: иначе нулевой счётчик закрытых вех выглядит поломкой.
