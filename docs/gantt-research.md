# Ресерч стека для «Проект под контролем» (16ч хакатон)

Дата: 2026-09-10. Формат: быстрый ресерч (4 параллельных трека, без глубокого разбора платных маркетплейсов и UX-бенчмарка — сознательно урезано под бюджет 16ч/10 рабочих часов).

Вводные: команда 5 человек (2 backend/Go, 2 frontend/Next.js, 1 девопс+аналитик+код), бюджет на лицензии не ограничен но бесплатное в приоритете, регламент разрешает любой сторонний код без ограничений.

## TL;DR — рекомендуемый стек

- **Gantt-рендер:** DHTMLX Gantt Community (MIT, бесплатно) — основной вариант; gantt-task-react (форк `@wamra`, MIT) — запасной.
- **Каскадный пересчёт дат, детект циклов, статусы, риск дедлайна, what-if:** писать самим на Go (~8.5 ч на 1 разработчика), готовых Go-библиотек для этого нет и не нужны — это ядро продукта, которое надо уметь объяснить жюри.
- **Backend:** скаффолд `go-blueprint` (chi/gin + Postgres + Docker) + `golang-migrate` + `sqlc` + `oapi-codegen`.
- **Frontend:** `Kiranism/next-shadcn-dashboard-starter` (MIT) как CRUD-каркас, вырезать демо/billing.
- **Контракт backend↔frontend:** OpenAPI-спека → `oapi-codegen` (Go) + `openapi-ts`/hey-api (TS-клиент) — экономит рассинхрон между 2+2 разработчиками.
- **Realtime:** SSE вручную (`net/http` + flusher), WebSocket не нужен для MVP-объёма.
- **Форк готового PM-приложения (Vikunja/OpenProject/Plane/Worklenz/Focalboard): не делать** — ни один кандидат не даёт извлекаемое ядро быстрее, чем сборка с нуля, и создаёт риск «не смогли объяснить архитектуру жюри».

Итоговая оценка инфраструктуры: ~2–2.5ч на бэкенд+фронт скаффолд, ~8.5ч на доменную логику Ганта (можно распараллелить между backend-разработчиками), ~4-6ч на интеграцию Gantt-компонента — укладывается в 10 рабочих часов при параллельной работе 5 человек.

## Трек A — Gantt-компоненты для React/Next.js

Проверено (2026-09-10): SVAR React Gantt, DHTMLX Gantt, Bryntum Gantt, Syncfusion React Gantt, gantt-task-react/форк wamra, Frappe Gantt, jsGantt-improved.

**Главный факт:** ни одна бесплатная библиотека не даёт каскадный пересчёт зависимостей «из коробки» — это либо платная PRO-фича (SVAR, DHTMLX), либо её вовсе нет (gantt-task-react, частично Frappe). Значит, пересчёт дат в любом случае пишется руками — выбор компонента сводится к рендер-движку + готовности к Next.js.

| Кандидат | Лицензия free | PRO цена | Каскад из коробки | Watermark в триале | Next.js готовность | Оценка интеграции |
|---|---|---|---|---|---|---|
| SVAR React Gantt | MIT (без каскада) | $749/dev | Нет | Да, 30 дней | Официальный туториал | 6-9ч (с каскадом) |
| **DHTMLX Gantt Community** | **MIT** | $699/dev | Нет | Да (PRO trial) | **Официальный Next.js стартер** | 5-8ч |
| Bryntum Gantt | нет free | $940/dev | Да, встроен | НЕ ПРОВЕРЕНО | React-обёртки есть | 6-8ч, дорого/сложно |
| Syncfusion React Gantt | Community license (условно, для орг. <$1M/≤5 dev) | $959/dev/год | Да, встроен | — | React-компоненты | 5-7ч, лицензия под вопросом для хакатон-команды |
| **gantt-task-react (wamra fork)** | **MIT** | — | Нет, свой код | Нет | Стандартный dynamic import | 5-7ч |
| Frappe Gantt | MIT | — | Частично (move_dependencies) | Нет | Нет офиц. React-обёртки | 4-6ч |
| jsGantt-improved | ISC | — | НЕ ПРОВЕРЕНО | Нет | НЕ ПРОВЕРЕНО | Не рекомендуется, низкая активность |

**Рекомендация:** DHTMLX Gantt Community — лучший баланс (все 4 типа связей FS/SS/FF/SF в бесплатной версии, официальный Next.js App Router стартер снижает риск «не завелось ночью»). Запасной вариант — gantt-task-react (wamra), если DHTMLX не заведётся: чище лицензия, но нет официальной интеграции с Next.js.

**Отброшены:** Bryntum (дорого, сложный enterprise API), Syncfusion (лицензионная неопределённость для команды без юрлица), SVAR (каскад только в платном PRO с водяным знаком), jsGantt-improved (низкая активность мейнтейнера).

## Трек B — Форк готового open-source PM-приложения

Проверено: Vikunja (Go+Vue), OpenProject (Rails+Angular), Worklenz (TS/Express+React), Plane (Django+Next.js), Focalboard (дисквалифицирован — Гант декоративный/отсутствует, MIT но проект без мейнтейнеров).

**Вердикт: форкать не стоит.** У всех одна и та же проблема для 16ч хакатона:
- либо стек далёк от Go+Next.js (OpenProject — Rails/Angular; Plane/Worklenz — не-Go бэкенд),
- либо инфраструктура разворачивается дольше бюджета (Plane — 9 контейнеров, ~4-8GB RAM; OpenProject — Rails-монолит, миграции),
- либо Гант-ядро физически не отделяется от остального продукта (Vikunja — Гант вплетён в общий API с auth/teams/labels; AGPL на публичном хакатон-репо создаёт лишние вопросы).

Единственный кандидат с доказанным полноценным каскадом+критическим путём — OpenProject, но его стек и объём монолита исключают форк за несколько часов.

**Что стоит подсмотреть (не форкать):** схему БД/API task-relations у Vikunja (github.com/go-vikunja/vikunja, Go) и алгоритм каскадного сдвига precedes/follows у OpenProject (модуль Gantt/relations) — 15-20 минут чтения кода ускорят проектирование собственной схемы.

## Трек C — Движок планирования (доменная логика)

**Рекомендация: писать самим, не подключать готовую Go-библиотеку.** Обоснование: нужный объём логики — ~150-250 строк Go (граф зависимостей, детект циклов, топосорт, каскадный пересчёт дат). Полноценный CPM (early/late start, float/slack) в требованиях кейса не нужен — только «сдвинулась ли итоговая дата проекта».

Найденные библиотеки (на случай, если понадобятся):
- Топосорт/циклы: [dominikbraun/graph](https://github.com/dominikbraun/graph) (Apache-2.0, активный) — избыточен для нужного объёма, но пригоден если нужен буст.
- Готовых production-grade Go-библиотек для CPM практически нет — везде пишут сами.
- Рабочие календари (если нужны выходные/праздники): [rickar/cal](https://github.com/rickar/cal) (BSD-3, 405★) — единственная позиция, где готовая либа реально экономит время (3-4ч на праздниках по странам).

**Оценка трудозатрат (1 backend-разработчик, упрощённый сценарий):**
| Компонент | Часы |
|---|---|
| Структуры данных + граф зависимостей | 1 |
| Детект циклов (DFS) | 1 |
| Топологический порядок (Kahn) | 0.5 |
| Каскадный пересчёт дат (FS + lag) | 2 |
| Статусы (done/in_progress/overdue/upcoming) | 0.5 |
| Риск дедлайна (сравнение project end до/после) | 0.5 |
| What-if превью (пересчёт на копии, без сохранения) | 1 |
| Юнит-тесты | 2 |
| **Итого** | **~8.5ч** |

Укладывается в 10 рабочих часов с запасом, особенно если распараллелить между 2 backend-разработчиками.

**Обязательные тест-кейсы:**
1. Прямой цикл A→B→A отклоняется.
2. Транзитивный цикл A→B→C→A отклоняется.
3. Топопорядок корректен для дерева с несколькими ветками.
4. Сдвиг end даты A сдвигает start прямых последователей (FS+lag).
5. Каскад долетает транзитивно через 2-3 звена цепочки.
6. Задача с несколькими предшественниками: start = max(end всех предшественников + lag).
7. Сдвиг задачи раньше срока не «утягивает» последователей раньше их текущего start.
8. status=overdue только если end в прошлом и status≠done; done никогда не помечается overdue.
9. What-if не мутирует исходные данные (пересчёт на копии).
10. Изменение, сдвигающее итоговую дату проекта, корректно детектит риск срыва дедлайна.

Структура данных и псевдокод каскадного пересчёта — см. полный вывод агента (доступен по запросу), базовая модель:
```go
type Task struct {
    ID, Name string
    Start, End time.Time
    Duration int
    DependsOn []Dependency // {TaskID, Type: FS/SS/FF/SF, LagDays}
    Status Status
}
```
Пересчёт: топологический обход подграфа от изменённой задачи по successors, `newStart = max(pred.End + lag)` по всем входящим FS-рёбрам.

## Трек D — Go+Next.js бойлерплейты и инфраструктура

**Главный факт:** готового объединённого Go+Next.js+Postgres+docker-compose шаблона с достаточной активностью не существует (единственный найденный неактивен с 2024, без лицензии). Экономить время нужно композицией отдельных частей, не поиском одного репо.

**Рекомендованная сборка:**
- **Backend:** `go-blueprint` (CLI-скаффолдер, MIT, генерирует chi/gin/fiber/echo + Postgres + Docker одной командой) + паттерны из `techschool/simplebank` (эталонный пример sqlc+goose+JWT, MIT) + `golang-migrate` для миграций + `sqlc` для типобезопасных запросов.
- **OpenAPI:** `oapi-codegen` (Go, Apache-2.0, активен) + `openapi-ts`/hey-api (TS-клиент, MIT) — экономит 2-3ч на синхронизации контрактов между параллельно работающими backend/frontend.
- **Realtime:** SSE вручную (`net/http`+flusher, ~30 мин) достаточно для «кто-то обновил задачу — обнови у всех»; полноценный WebSocket (`coder/websocket`, бывший nhooyr) оправдан только для live drag-n-drop с нескольких клиентов одновременно — не нужен для MVP.
- **Frontend:** `Kiranism/next-shadcn-dashboard-starter` (MIT, Next.js 16, готовые CRUD-таблицы TanStack Table, формы React Hook Form+Zod, обновлён 2026-08-24) — вырезать billing/demo-страницы, оставить layout+таблицу+форму+модалку.
- **Docker Compose:** готового шаблона нет — собрать самим (postgres+api+web), 20-30 минут, не узкое место.

**Оценка времени:**
- С рекомендованным стеком: ~2-2.5ч на весь инфраструктурный скаффолд.
- С нуля: ~5-6ч.
- Экономия: ~3-3.5ч из 10 рабочих — почти треть бюджета.

## Матрица «требование кейса → чем закрывается»

| Требование | Чем закрывается |
|---|---|
| 1. Проект: название, сроки | Свой CRUD на Go + shadcn-форма (стартер) |
| 2. Задачи CRUD, ответственный, статус | Свой CRUD на Go (sqlc) + TanStack Table (стартер) |
| 3. Гант: даты/длительность/статус/связи | DHTMLX Gantt Community (рендер) + свои данные с backend через OpenAPI-клиент |
| 4. Зависимости + видимость затронутых задач | Свой Go-движок (граф, топосорт, каскадный пересчёт) — трек C |
| 5. Контроль состояния + риск срыва | Свой Go-движок (статусы + сравнение project end до/после) — трек C |
| 6. Сценарий «что если» | Свой Go-движок, what-if превью на копии графа без сохранения — трек C |

Ключевой вывод: требования 4-6 (самая сложная и самая оцениваемая часть кейса) закрываются исключительно собственным кодом — ни один сторонний компонент их не решает за вас. Это одновременно и риск (нужно успеть написать и протестировать), и преимущество на защите (жюри увидит, что команда владеет архитектурой, а не спрятала логику в чужой PRO-библиотеке).

## Список отброшенных кандидатов (сводно)

- **Bryntum Gantt** — дорого ($940+/dev), сложный API, неясные условия trial.
- **Syncfusion React Gantt** — лицензионная неопределённость Community License для хакатон-команды без юрлица.
- **SVAR React Gantt** — каскад только в платном PRO с водяным знаком на триале.
- **jsGantt-improved** — низкая активность мейнтейнера.
- **Vikunja / OpenProject / Plane / Worklenz — форк целиком** — стек далёк от Go+Next.js и/или инфраструктура не поднимается за отведённое время и/или ядро не извлекается без переноса монолита.
- **Focalboard** — Гант декоративный/отсутствует, проект без активных мейнтейнеров.
- Полноценный CPM (early/late start, slack/float, ресурсное планирование) — избыточен для требований кейса, не нужен.
- Готовый монорепо-бойлерплейт Go+Next.js — не найден активный кандидат, собрано композицией отдельных частей.

## Открытые вопросы

Раздел 0 промпта закрыт (16ч/10 рабочих часов, команда 5 человек 2+2+1, бюджет не ограничен, регламент разрешает любой сторонний код). Остаётся уточнить по ходу разработки:
- Нужны ли рабочие календари (выходные/праздники) в расчёте сроков, или достаточно календарных дней — от этого зависит, нужен ли `rickar/cal` (+1ч).
- Нужен ли live-realtime между несколькими пользователями одновременно (WebSocket) или достаточно обновления по действию пользователя (SSE/просто рефетч) — упрощает или усложняет трек D.
