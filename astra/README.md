# Запуск taygant на Astra Linux SE 1.8 «Воронеж» (ЗПС + PARSEC)

Стек taygant (PostgreSQL + backend + frontend) разворачивается на Astra Linux
Special Edition 1.8 в режиме **Воронеж** с включёнными **ЗПС** (замкнутая
программная среда, модуль ядра `digsig_verif`) и **PARSEC** (мандатный доступ).

Обычный `docker compose up` на такой машине не заработает по двум причинам:

1. **ЗПС блокирует исполнение неподписанных файлов — включая файлы внутри
   контейнеров.** Бинарники из официальных образов (alpine, postgres, node)
   не подписаны ключами Астры, поэтому ядро не даст им запуститься.
2. **Docker нужен в rootless-режиме** — под PARSEC контейнеры должны работать
   от непривилегированного пользователя (это же рекомендует документация Астры).

Поэтому здесь:
- контейнеры запускаются **rootless Docker** (`dockerd-rootless`, systemd `--user`);
- сеть — **host** (`--network=host`), сервисы общаются по `127.0.0.1`;
- файлы сервисов **подписываются** самогенерированным ключом ГОСТ Р 34.10-2012
  (подпись в расширенных атрибутах + отсоединённая подпись);
- все зависимости и образы **скачиваются заранее** и переносятся на машину
  без интернета.

Обычный `docker compose up --build` не меняется и продолжает работать.

## Архитектура

```
┌─ Машина с интернетом ──────────────────────────┐
│ offline/export-images.sh    → images.tar.gz     │
│ offline/export-apt-deps.sh  → apt-deps.tar.gz   │
└─────────────────────────────────────────────────┘
                        │  (перенос, например по USB)
                        ▼
┌─ Astra Linux SE 1.8 «Воронеж» (ЗПС + PARSEC, без интернета) ──┐
│                                                                │
│  Пользователь taygant (не root)                                │
│  ~/taygant/                                                    │
│   ├── keys/            — пара ключей подписи (секретный здесь!)│
│   ├── signatures/      — манифесты подписанных файлов          │
│   ├── staging/         — временные ФС образов для подписи      │
│   ├── data/postgres/   — данные БД                             │
│   └── .env.astra       — конфигурация (JWT_SECRET и т.п.)      │
│                                                                │
│  /etc/digsig/                                                  │
│   ├── xattr_keys/            — публичный ключ                  │
│   ├── keys/legacy/keys/      — тот же ключ (legacy-формат)     │
│   └── external_sig/          — отсоединённые подписи           │
│         @usr@local@bin@app.sign  (пути ВНУТРИ контейнеров)     │
│                                                                │
│  Rootless Docker (systemd --user, linger)                      │
│  Контейнеры: --network=host, обычный запуск образов            │
│   postgres  → 127.0.0.1:5432                                   │
│   backend   → 127.0.0.1:4000                                   │
│   frontend  → 0.0.0.0:3000                                     │
└────────────────────────────────────────────────────────────────┘
```

Ключевая идея: процессы в контейнерах — те же процессы хоста, и ядро при
включённой ЗПС проверяет их при запуске. Поэтому каждый исполняемый файл и
скрипт из образов подписывается заранее, а подписи (по путям внутри
контейнеров) кладутся на хост в `/etc/digsig/external_sig` — там их находит
модуль ядра `digsig_verif`.

## Что нужно

- Astra Linux SE 1.8 (Воронеж), установка с PARSEC, доступ по ssh.
- На период подготовки — доступ в интернет **либо** с самой Astra, либо с
  другой машины (оттуда переносится архив образов).
- Ключ подписи ЗПС генерируется прямо на целевой Astra (`keys/gen-keys.sh`).
  Это самогенерированный ключ — по документации Астры он проверяет подписи в
  расширенных атрибутах и отсоединённые подписи (но не встраиваемые в ELF).

## Подготовка на машине с интернетом

### 1. Образы (любая машина с Docker и исходниками проекта)

```bash
astra/offline/export-images.sh /путь/к/выводу
```

Результат — `images.tar.gz` с образами:
`taygant-postgres:astra`, `taygant-backend:astra`, `taygant-frontend:astra`.

> Фронтенд для Astra собирается отдельным тегом: в него зашивается
> `BACKEND_URL=http://127.0.0.1:4000` (host-сеть), а не `http://backend:4000`.

### 2. apt-пакеты (лучше — на самой Astra, пока есть интернет)

```bash
astra/offline/export-apt-deps.sh /путь/к/выводу
```

Результат — `apt-deps.tar.gz` (`.deb` + все зависимости: rootless Docker,
`bsign`, `gnupg` и т.п., список в `astra/offline/packages.list`).

Перенесите оба архива на целевую Astra (флешка, scp до отключения сети).

## Развёртывание на Astra (пошагово)

### 4.1. Установка rootless Docker оффлайн

```bash
# в домашнем каталоге пользователя, который будет «владельцем» контейнеров
mkdir -p ~/taygant
cd ~/taygant

# распакуйте .deb и скрипты проекта (проект — отдельно, например из git)
tar -xzf apt-deps.tar.gz            # → debs/
/path/to/repo/astra/setup/install-rootless-docker.sh debs
```

Скрипт: ставит пакеты из локальных `.deb`, назначает диапазоны
subordinate uid/gid, включает user namespaces, запускает systemd-юнит
`docker.service` (rootless) и включает `loginctl enable-linger` (демон стартует
при загрузке без входа пользователя).

Проверка:

```bash
docker info | head -20        # должна быть строка rootless / не требовать sudo
systemctl --user status docker
```

> Внимание: пользователь, из-под которого выполняется скрипт, и будет
> владельцем контейнеров. Дальше все команды выполняются от этого же
> пользователя (root не нужен; `sudo` — только на привилегированных шагах).

### 4.2. Загрузка образов

```bash
astra/setup/load-images.sh ~/taygant/images.tar.gz
docker images | grep taygant
```

### 4.3. Конфигурация

```bash
cp astra/.env.astra.example ~/taygant/.env.astra
# заполните JWT_SECRET:  openssl rand -hex 32
```

### 4.4. Ключи подписи

```bash
astra/keys/gen-keys.sh
```

Создаётся пара ГОСТ Р 34.10-2012 без пароля (пароль — через `SIGN_PASSPHRASE`
в `.env.astra`). Результат в `~/taygant/keys/`:
`KEYID`, `taygant-pub.gpg`, `taygant-revoke.rev`.
Секретный ключ остаётся в связке gpg этого пользователя.

### 4.5. Подпись образов

```bash
astra/keys/sign-images.sh
```

Для каждого образа: экспорт содержимого → подпись всех ELF/скриптов
отсоединённой подписью → подписи переименовываются по путям **внутри
контейнера** и кладутся в `/etc/digsig/external_sig/` (через sudo).

Проверка подписей:

```bash
astra/keys/verify-signatures.sh
```

> Пока ЗПС выключена, этот шаг можно пропустить — но тогда перед включением
> ЗПС его обязательно нужно выполнить (см. п. 4.6).

### 4.6. Регистрация ключа и включение ЗПС

```bash
astra/setup/register-keys.sh      # ключ в /etc/digsig + пересборка initramfs
astra/setup/enable-zps.sh         # astra-digsig-control enable
sudo reboot
```

**Порядок важен**: сначала подпись, потом ключ в ядро, потом включение ЗПС.

### 4.7. Запуск

```bash
# после перезагрузки, из-под того же пользователя
astra/run/up.sh
astra/run/status.sh
```

Приложение: `http://<IP_ASTRA>:3000` (логин/пароль — из демо-сидинга, см.
backend; в пустой БД создаются демо-данные при первом старте).

## Как это работает

**ЗПС** (модуль ядра `digsig_verif`) проверяет подпись файла при его запуске
или открытии. Подписи бывают трёх видов: встроенные в ELF, в расширенных
атрибутах (xattr), отсоединённые. Самогенерированные ключи поддерживают только
последние два. Для файлов внутри контейнеров мы используем **отсоединённую
подпись**:

- `bsign -s -D` пишет подпись в отдельный файл, имя которого = путь к файлу,
  где `/` заменён на `@` (для `/usr/local/bin/app` → `@usr@local@bin@app.sign`);
- подписи кладутся на **хост** в `/etc/digsig/external_sig/`, публичный ключ —
  в `/etc/digsig/xattr_keys/`;
- при запуске процесса в контейнере ядро находит подпись по пути файла
  (как его видит процесс) и проверяет содержимое. По документации Астры
  результат проверки отсоединённой подписи не зависит от того, где физически
  лежит файл — поэтому для файлов из образов это работает.

Почему не подписи «внутри» образа и не xattr: `docker export`/`import` не
переносит расширенные атрибуты, а bind-mount каталога в корень контейнера
(`docker run -v dir:/`) Docker запрещает. Отсоединённые подписи на хосте
работают в любом случае, образы запускаются как обычно.

Сеть — `--network=host`, поэтому имена сервисов compose (`backend`) не нужны:
фронтенд проксирует `/backend/*` → `http://127.0.0.1:4000` (это зашито в образ
при сборке), backend ходит в БД на `127.0.0.1:5432`.

## Проверка работы под ЗПС

До включения ЗПС (`astra/run/up.sh` + `status.sh`) стек должен работать —
это базовая проверка. После включения ЗПС и перезагрузки:

```bash
astra/run/up.sh            # контейнеры должны подняться (значит подписи верны)
astra/run/status.sh        # все смоук-проверки OK
astra/keys/verify-signatures.sh
```

Если какая-то программа внутри контейнера не запускается из-за ЗПС, в логах
ядра будет примерно `Operation not permitted` / `digsig` при запуске процесса:
```bash
sudo journalctl -k | grep -i digsig
docker logs taygant-backend
```

Типичный случай — подпись не покрыла какой-то скрипт: перезапустите подпись
(`astra/keys/sign-images.sh <сервис>`), затем `setup/register-keys.sh`,
`update-initramfs` и перезагрузку.

## Диагностика

| Симптом | Причина / решение |
|---|---|
| `docker info` ругается на демон | `systemctl --user status docker`, `journalctl --user -u docker -n 50`; юнит стартует после перелогина или `loginctl enable-linger` |
| `up.sh` пишет «rootless Docker не отвечает» | перелогиньтесь, проверьте `docker context ls`; при необходимости `dockerd-rootless-setuptool.sh install` ещё раз |
| контейнер не стартует после включения ЗПС | `sudo journalctl -k \| grep -i digsig`; переподписать сервис, `register-keys.sh`, reboot |
| backend стартует, а frontend нет | `docker logs taygant-frontend`; проверьте `BACKEND_URL` в образе (`docker inspect taygant-frontend:astra`) |
| `verify-signatures.sh` ругается на отсутствие подписей | выполните `keys/sign-images.sh`, затем `setup/register-keys.sh` и перезагрузку |
| потерялись данные БД | они в `~/taygant/data/postgres` (том `-v`), контейнеры можно пересоздавать |

Если под ЗПС падает что-то, чего нет в подписях (например, новый скрипт),
добавьте подписи и обновите список в ядре:
`astra/keys/sign-images.sh <сервис>` → `sudo update-initramfs -uk all` → reboot.

## Откат

Отключение ЗПС (если что-то пошло не так):

```bash
sudo astra-digsig-control disable     # или astra-zps-control disable
sudo reboot
```

Данные и образы при этом не теряются. Остановить стек: `astra/run/down.sh`
(данные БД остаются в `~/taygant/data/postgres`).

| `setup/install-rootless-docker.sh debs` | оффлайн-установка rootless Docker + bsign | Astra (от пользователя) |

| `keys/gen-keys.sh` | пара ключей ГОСТ Р 34.10-2012 | Astra |
| `keys/sign-images.sh [сервис]` | подписать ФС образов | Astra |
| `keys/sign-files.sh <файлы>` | подписать произвольные файлы/каталоги на хосте | Astra |
| `keys/verify-signatures.sh` | контроль подписей (по манифестам) | Astra |
| `setup/register-keys.sh` | ключ в `/etc/digsig` + initramfs | Astra (sudo) |
| `setup/enable-zps.sh` | `astra-digsig-control enable` | Astra (sudo) |

| `run/down.sh` | остановка/удаление контейнеров | Astra |
| `run/status.sh` | статус + смоук-тест | Astra |
| `run/healthcheck.sh` | только смоук-тест | Astra |

Переменные настройки — в `~/taygant/.env.astra` (образец: `astra/.env.astra.example`).
